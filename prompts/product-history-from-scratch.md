# 제품이력 조회 도우미를 기능 프롬프트로 처음부터 만들기

대상: **Google Cloud → Agent Studio → 앱 빌더**. 기준일: 2026-10-21.

기존 앱 전체 코드나 수정용 ZIP을 붙이지 않는다. 새 앱에서 아래 프롬프트를 순서대로 사용하고 각 단계의 기능을 확인한다. 기존 앱과 배포된 Agent는 유지한다. 참조 코드는 마지막 단계의 A2A 요청 JSON 한 개로 제한한다.

## 준비

현재 교육생 프로젝트에서 실제 Agent를 호출하는 연결 서버의 `${BRIDGE_BASE_URL}`을 준비한다. 이 서버는 서버 측에서 인증하며 `/api/agent/v1/card`, `/api/agent/v1/message:send`, `/api/agent/v1/tasks/{id}`를 제공한다. 계정별 Agent를 확인한 주소를 사용한다. 토큰·API 키·개인정보는 프롬프트나 공개 저장소에 넣지 않는다.

## 1. 데이터와 조회 화면 만들기

```text
교육용 '제품이력 조회 도우미 - 프롬프트 기본형'을 새로 만들어 주세요.
앱 빌더 기본 환경과 기본 UI 구성으로 만들고 추가 패키지는 사용하지 마세요.
기존 소스를 복사하지 말고 아래 기능 요구로 구현해 주세요.

화면에는 S/N 또는 모델 질문 입력창, 조회 범위(생산이력/SW이력/통합),
조회 버튼, 결과 표, 조회 근거 영역, 새 대화 버튼만 있으면 됩니다.
한글 UI로 하고 모든 자료를 '교육용 더미 데이터'라고 표시해 주세요.

ERP 더미 20행과 SW 변경이력 더미 10행을 만드세요.
ERP 필드: 원본 행번호, S/N, 모델, Main 버전, AP 버전, 프로그램 버전,
제조일, 출고일, 가상 거래처.
SW 필드: 원본 행번호, 문서번호, 모델, 등록일, 보드(Main/AP), 버전, 변경구분.

다음 검증 자료는 정확히 포함하세요.
ERP #1: AK000001-20260001, BC380, Main V0.25.6,
AP BC380.AP.1.6.C0.007.N.ML_CONNECT, 프로그램 3.1.14.056,
제조일 2026-01-20, 출고일 2026-02-25, 거래처_0001.
ERP #2: AK000002-20260002, BC380PRO. BC380과 별도 모델입니다.
ERP #4: AK000004-20260004, BC380, Main/AP/프로그램 버전은 공란입니다.
SW에는 BC380 AP C0.007(2026-01-10), BC380 AP C0.010(2026-03-10),
BC380 Main V0.25.8(2026-03-11)과 BC380PRO 전용 이력을 포함하세요.
나머지는 가상 자료로 생성하되 S/N은 서로 다르게 하세요.

이번 단계는 로컬 조회 화면까지만 만듭니다. 아직 AI 답변은 만들지 마세요.
package.json, lockfile, Dockerfile이나 빌드 도구 버전은 수정하지 마세요.
만든 기능과 생성한 데이터 행 수를 알려 주세요.
```

## 2. 정확한 조회와 대화 이어가기

```text
현재 화면과 자료를 유지하고 조회 규칙과 대화 이어가기를 완성해 주세요.

S/N은 앞뒤 공백을 제거하고 전체값으로 정확히 일치시킵니다.
모델명을 S/N으로 처리하거나 부분일치로 다른 장비를 선택하지 마세요.
BC380과 BC380PRO도 정확히 구분합니다.
ERP에서 고른 장비의 모델과 정확히 같은 SW 이력만 연결합니다.
SW 이력은 등록일 내림차순으로 보여 주고 원본 행번호와 문서번호를 표시합니다.
공란은 '자료 없음'으로 표시하고 버전·날짜를 추정하지 마세요.
최신 등록 버전이 실제 장비에 적용 완료된 버전이라고 단정하지 마세요.

한 장비를 조회한 뒤 '그 장비 제조일은?'이라고 물으면 마지막 장비를 유지합니다.
다른 S/N을 명시하면 그 장비로 전환합니다.
새 대화를 누르면 마지막 장비와 대화 기록을 초기화합니다.
질문이 모호하거나 모델만 입력했다면 장비를 임의로 고르지 말고 범위를 안내합니다.

통합 조회 시 현재 선택 장비 ERP 1행과 같은 모델 SW 행만 근거에 담으세요.
전체 데이터를 매번 AI로 보낼 필요는 없습니다.
아직 외부 AI 호출은 하지 마세요. 조회와 근거 표시만 검증합니다.
```

## 3. 실제 Agent 연결 — 유일한 코드 참고

`${BRIDGE_BASE_URL}`만 실제 확인한 주소로 바꾼다. 아래 JSON은 이미 검증한 요청 규약이다. 기존 구현 전체를 복사할 필요가 없다.

```text
현재 조회 기능·자료·UI를 유지하고 실제 Agent 응답을 연결해 주세요.
연결 서버 기본 주소는 ${BRIDGE_BASE_URL} 입니다.
GET /api/agent/v1/card로 Agent 카드의 name/protocolVersion/skills를 확인하고
실제로 성공했을 때만 'Agent 연결됨'을 표시하세요.

질문과 현재 조회 근거를 합친 문자열을 아래 규약으로 전송하세요.
POST /api/agent/v1/message:send
Content-Type: application/json

{
  "message": {
    "messageId": "매 요청마다 생성한 UUID",
    "role": "ROLE_USER",
    "content": [{"text": "사용자 질문과 선별한 ERP/SW 근거"}]
  },
  "configuration": {"blocking": true}
}

응답에서 받은 contextId가 있을 때만 다음 요청의 message.contextId에 넣습니다.
새 대화 또는 다른 장비로 전환하면 contextId를 비웁니다.
서버 응답은 raw/task/result 안의 task를 확인하고 status.state 또는 status 문자열을 읽으세요.
완료 상태는 COMPLETED 또는 TASK_STATE_COMPLETED입니다.
완료 답변은 artifacts[].parts[].text 또는 artifacts[].content[].text에서 읽습니다.
답변이 없을 때에는 Agent 역할의 message/history 내용만 확인하세요.
사용자가 보낸 근거를 Agent의 답변으로 표시하지 마세요.

아직 진행 중이고 작업 ID가 있을 때만 GET /api/agent/v1/tasks/{id}로 확인합니다.
2초부터 간격을 늘리고 60초가 지나면 대기 초과를 표시하세요.
HTTP 오류, 응답 내부 error, 실패 상태와 429는 오류로 표시합니다.
자동으로 Gemini 직접 호출이나 가짜 답변으로 대체하지 마세요.

전송부터 실제 답변 표시까지 소요된 시간을 초 단위로 보여 주세요.
전송 중에는 중복 조회를 막고 완료/오류 후 다시 질문할 수 있게 하세요.
이번에는 위 통신 연결에 필요한 최소 코드만 생성하세요.
```

## 배포와 측정

기능 검증 후 앱 빌더의 Cloud Run 배포 버튼을 한 번 시험한다. Preview와 실제 Cloud Build·배포·Agent 응답은 각각 기록한다. 기본 템플릿의 npm 설치 오류가 나면 그 로그를 별도 플랫폼 문제로 남기고, 기능 프롬프트에 빌드 의존성 우회 코드를 계속 덧붙이지 않는다.

외부 연결 서버를 사용하는 경우 새 미리보기/배포 origin을 연결 서버에서 허용해야 할 수 있다. 이는 앱의 답변 생성 로직과 별도의 서버 설정이며 CORS 실패를 모델 대체로 감추지 않는다.
