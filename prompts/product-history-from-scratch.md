# 제품이력 조회 도우미: 기능 요구로 처음부터 생성하기

대상: **Google Cloud → Agent Studio → 앱 빌더**. 기준일: 2026-10-21.

이미 ERP 20행·SW 10행이 생성된 기본형은 [저장된 앱에서 이어가는 프롬프트와 재개 검증 기록](product-history-resume.md)을 사용한다. 아래 최초 시도 기록과 이후 재개 결과를 구분한다.

기존 앱 전체 코드·ZIP을 가져오거나 빌드 의존성 우회를 덧붙이지 않는다. 아래 초기 프롬프트로 필요한 기능을 생성하고, 실제 화면에서 확인한 문제만 짧은 후속 프롬프트로 수정한다. 참조 코드는 **A2A 요청 JSON 한 개**로 제한한다.

## 준비

- 새 앱에서 시작하고 기존 정상 앱과 실제 Agent는 유지한다.
- `${BRIDGE_BASE_URL}`을 해당 교육생 Agent를 호출하도록 검증한 연결 서버 주소로 바꾼다.
- 연결 서버가 서버 측 인증과 `/api/agent/v1/card`, `/api/agent/v1/message:send`, `/api/agent/v1/tasks/{id}`를 제공하는 것이 전제다. 이 프롬프트가 인증 서버까지 새로 만드는 것은 아니다.
- API 키·토큰·실제 사내 자료는 입력하거나 공개 저장소에 올리지 않는다.

## 초기 프롬프트 — 전체 필수 기능 생성

아래 블록 하나를 새 앱의 '여기에 앱 정의'에 붙인다. 개발 환경이나 기존 소스 대신 사용자가 원하는 기능을 지정한다.
```text
앱 빌더 기본 환경에서 한글 교육용 '제품이력 통합 조회 도우미 - 프롬프트 기본형'을
처음부터 만들어 주세요. 기존 소스·ZIP은 사용하지 않습니다. 추가 패키지와 빌드 설정
수정 없이 필수 기능만 구현하세요. 답변은 아래 실제 Agent에서만 받습니다.

[더미 데이터]
ERP 20행: 원본 행번호, S/N, 모델, Main/AP/프로그램 버전, 제조일, 출고일, 가상 거래처.
SW 10행: 원본 행번호, 문서번호, 모델, 등록일, 보드(Main/AP), 버전, 변경구분.
ERP #1은 AK000001-20260001 / BC380 / Main V0.25.6 /
AP BC380.AP.1.6.C0.007.N.ML_CONNECT / 프로그램 3.1.14.056 /
제조 2026-01-20 / 출고 2026-02-25 / 거래처_0001로 만드세요.
ERP #2는 AK000002-20260002 / BC380PRO로, #4는 AK000004-20260004 / BC380으로
만들고 #4의 버전 3개는 공란으로 두세요. 나머지는 중복 S/N 없는 가상 자료입니다.
SW에는 BC380 AP C0.007(2026-01-10), AP C0.010(2026-03-10),
Main V0.25.8(2026-03-11) 및 BC380PRO 전용 이력을 포함하세요.
모든 화면에 교육용 더미임을 표시합니다.

[조회와 문맥]
S/N 전체값과 모델명은 각각 정확히 일치시킵니다. BC380과 BC380PRO를 섞거나
모델명을 S/N으로 오인하지 마세요. 장비를 임의로 선택하지 않습니다.
장비 조회 후 '그 장비 제조일은?'은 마지막 장비를 유지합니다.
다른 S/N 또는 새 대화에서는 이전 장비와 Agent contextId를 초기화합니다.
장비가 없거나 질문이 모호하면 안내합니다. 공란은 '자료 없음'으로 유지합니다.
선택 장비 ERP 1행과 정확히 같은 모델 SW 이력만 선별하고 원본 행번호를 표시합니다.
최신 SW 등록 이력과 실제 장비에 적용된 버전을 구분하며 근거 없는 값을 만들지 않습니다.

[실제 Agent 연결]
연결 서버: ${BRIDGE_BASE_URL}
서버가 인증을 담당하므로 브라우저에 토큰/API 키를 넣지 않습니다.
GET /api/agent/v1/card의 name/protocolVersion/skills가 확인될 때만 연결됨을 표시합니다.
질문과 선별한 근거를 합친 문자열을 아래 규약으로 전송하세요. 이것이 유일한 코드 참고입니다.
POST /api/agent/v1/message:send, Content-Type: application/json
{
  "message": {
    "messageId": "요청별 UUID",
    "role": "ROLE_USER",
    "content": [{"text": "질문과 선별한 ERP/SW 근거"}]
  },
  "configuration": {"blocking": true}
}
응답 contextId가 있으면 동일 장비의 후속 요청 message.contextId에 넣습니다.
응답은 raw/task/result 안의 task를 확인하고 status.state 또는 status 문자열을 읽습니다.
COMPLETED/TASK_STATE_COMPLETED 때 artifacts의 parts/content 안 text를 답변으로 표시합니다.
그곳에 없으면 Agent 역할의 message/history에서만 답변을 찾습니다.
사용자 근거를 답변처럼 표시하거나 Gemini 직접 호출·가짜 성공으로 대체하지 마세요.
작업이 진행 중이고 ID가 있을 때만 GET /api/agent/v1/tasks/{id}를 2초부터 간격을
늘려 조회하고 60초에 종료합니다. HTTP 오류·내부 error·실패 상태·429는 오류로 표시합니다.

[최소 화면]
질문 입력창, 조회 범위(생산이력/SW이력/통합), 질문 버튼, 대화 기록,
현재 장비와 선별한 근거 표, 새 대화 버튼을 만드세요.
전송 중에는 중복 질문을 막고 로딩을 표시합니다. 최종 답변까지의 실제 소요 초를 표시합니다.
먼저 기본 장비 통합 조회, 후속 제조일, PRO 모델 분리, 공란 유지, 새 대화를 확인할 수 있게 하세요.
과도한 대시보드·장식·추가 기능은 만들지 마세요. 생성 결과와 미확인 항목을 구분해 보고하세요.
```

## 짧은 후속 수정 프롬프트

새 기능을 계속 더하지 말고 실제 실패한 검증 항목만 적는다.

```text
기존 기능·자료·기본 환경을 유지하고 다음 문제만 고쳐 주세요.
[실제로 수행한 질문/입력]
[화면에서 확인한 문제]
[기대 결과와 근거 행]
전체 앱을 다시 작성하거나 직접 Gemini 호출·가짜 답변으로 우회하지 마세요.
변경 파일과 실제로 확인한 결과, 확인하지 못한 항목을 구분해 주세요.
```

예: 'BC380PRO 조회에 BC380 이력이 섞입니다. 모델을 전체값으로 정확히 일치시키고 나머지는 유지해 주세요.'

## 기능 확인 순서

| 확인 | 기대 결과 |
| --- | --- |
| AK000001-20260001 통합 조회 | ERP #1, BC380 SW만 근거로 사용. 출고일 2026-02-25와 최신 등록 이력을 구분 |
| 그 장비 제조일은? | 마지막 장비 유지, 2026-01-20, ERP #1 |
| AK000002-20260002 | BC380PRO 전용 근거. BC380 이력 혼합 없음 |
| AK000004-20260004 | 버전 공란 유지. 값 생성 없음 |
| 모델 BC380만 입력 | S/N으로 오인하거나 장비를 임의로 선택하지 않음 |
| 새 대화 | 마지막 장비·대화 기록·Agent context 초기화 |
| 연결/Agent 오류 | 실제 오류 표시. 사용자 근거를 AI 답변으로 재사용하지 않음 |

외부 연결 서버는 새 미리보기/배포 origin을 허용해야 할 수 있다. 이는 서버 설정이며 앱 기능 생성 프롬프트와 구분한다. CORS 실패를 모델 대체로 감추지 않는다.

## 배포와 속도 측정

기능 확인 후 앱 빌더의 Cloud Run 배포 버튼으로 시험한다. Preview, Cloud Build, 배포 URL, 실제 Agent 응답은 각각 검증한다. 기본 템플릿 npm 오류가 발생하면 로그를 별도 플랫폼 문제로 남기고, 기능 프롬프트에 빌드 우회 코드를 계속 추가하지 않는다.

통합 질문과 후속 질문의 소요 시간은 따로 기록한다. 첫 연결, 실패, 재시도와 정상 완료를 섞어 평균내지 않는다. 실제 완료되지 않은 답변의 시간을 성공 측정치로 쓰지 않는다.

## 실제 실행 기록 — 2026-10-21

| 작업 | 실제 결과 |
| --- | --- |
| 전체 코드 첨부 없이 새 앱의 화면·데이터 생성 | 성공. 프롬프트만으로 기본 UI와 ERP 20행·SW 10행 생성·저장 |
| 기본 데이터 화면 확인 | ERP #1의 지정 S/N·버전·제조일·출고일, #2 PRO 모델, #4 버전 공란과 SW 10행을 확인 |
| 기본 앱에서 AK000001-20260001 조회 | ERP 1행 조회됨. SW는 0행으로, 장비 모델을 통한 SW 연결 규칙은 아직 추가되지 않은 상태임을 확인 |
| 조회 규칙·문맥을 추가하는 후속 생성 | gemini-3.8-flash 및 대체 gemini-3.7-flash에서 Resource has been exhausted 오류, 이전 체크포인트로 복원 |
| 위 통합 초기 프롬프트로 별도 새 앱 생성 | 같은 할당량 오류로 실패. 전체 기능 생성 성공으로 취급하지 않음 |
| 새 앱의 실제 Agent 연결·후속 질문·속도·Cloud Run 배포 | 미실행. 생성 단계의 할당량 문제가 해결된 뒤 진행해야 함 |
| 새 앱 소스 직접 수정 | 하지 않음. 프롬프트 생성 원칙 유지 |

위 JSON 통신 규약은 기존 실제 Agent 연결 구현에서 확인한 최소 참고이며, 새 앱의 연결 성공을 대신 증명하지 않는다. 모델 할당량과 기본 배포 템플릿 문제를 기능 코드 오류로 혼동하지 않는다. 추가 로그인이나 결제 변경은 진행하지 않았다.
