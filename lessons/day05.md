# 5일차 기업 문제 해결 과정 회고와 실행 로드맵

운영 예정일은 2026년 10월 28일 수요일 13:00~17:00이다. 활동 210분과 휴식 30분으로 구성한다. 이 문서는 수업 운영안이며 실시 결과나 교육생 전원의 성취를 기록한 문서가 아니다.

이번 과정은 셀바스헬스케어의 실제 업무 문제를 함께 풀어 보는 PBL 기반 컨설팅이다. 교육생은 현업 문제와 자료를 제공하고 실험 결과를 판단하는 주체다. 컨설턴트는 질문을 구체화하고, 검증 방법을 제안하며, 막힌 지점의 원인과 다음 선택을 함께 정한다. 5일차에는 그동안의 선택과 결과를 돌아보고 회사가 이어갈 실행 계획을 만든다.

## 1 우리가 함께 해결하려던 문제

직원이 특정 장비의 출고일과 탑재 SW를 확인하려면 ERP 제품 정보와 SW 변경통보 자료를 대조해야 한다. 장비 식별자가 불완전하거나 자료의 날짜·버전 의미가 다르면 답을 잘못 연결할 수 있다. 우리가 시도한 제품이력 도우미의 목적은 직원이 장비를 정확히 식별하고, 원천 근거를 확인하며, 자료로 알 수 없는 내용도 구분하도록 돕는 것이다.

함께 확인할 업무 흐름은 다음과 같다.

직원 질문 → 전체 S/N과 모델 확인 → ERP 장비 행 조회 → 같은 모델의 SW 자료 대조 → 근거와 확인 불가 안내 → 필요한 담당자에게 확인 요청.

자동 동기화, 직원별 대화와 중앙 이력, A/S 이력, 모바일 입력은 현업에서 제시한 후속 요구다. 현재 시제품만으로 이 요구가 모두 해결되었다고 판단하지 않는다. 업무 시간이 얼마나 줄었는지와 오류가 얼마나 감소했는지도 같은 조건의 수작업 비교가 있어야 성과로 말할 수 있다.

팀은 시작할 때 한 문장을 완성한다. “우리의 ___ 담당자가 ___ 상황에서 ___ 자료를 찾느라 ___ 어려움을 겪는다. 이번 시제품으로 ___ 판단을 돕고자 했다.” 실제 담당과 빈도를 모르면 현업 확인 과제로 남긴다.

## 2 그동안의 시도와 도달 지점

아래는 자료에서 확인한 작업이다. 각 팀은 자신이 직접 수행한 항목과 강사 시연·저장된 결과로 확인한 항목을 따로 표시한다.

| 과정 | 문제를 풀기 위해 한 시도 | 확인한 결과와 한계 |
| --- | --- | --- |
| 1일차 자료와 정답 | 업무 질문을 원천 행·필드와 연결하고, 식별자·빈값·중복 처리와 Agent 지침을 정리했다. | 답의 근거와 예외를 먼저 정하는 방법을 다뤘다. 최종 지침 전체 시험과 개인별 수행은 기록을 확인해야 한다. |
| 2일차 실제 연결 | ERP·SW 조회와 후속 질문을 A2A 채팅으로 확인하고 인증·리전·CORS·503·429를 나눠 봤다. | 일부 질문의 실제 응답을 확인했다. 파일 스냅샷 조회와 임시 인증 사례이며 전체 정확도·상시 운영·전원 재현을 입증하지 않는다. |
| 3일차 지연과 갱신 | 고정응답과 제품이력 질문을 나눠 측정하고, 호출·폴링과 자료 선별 방식을 바꿔 결과를 비교했다. | 측정한 조건의 개선 기록이 있다. 서로 다른 앱·질문·표본의 시간을 합치지 않는다. 자동 갱신·사용자 분리·대규모 성능은 별도 과제다. |
| 4일차 공통 기준과 배포 | 구현 차이를 줄이려고 Cloud Agent 중심의 공통 기준을 정하고 프롬프트 생성·실제 응답·ZIP 배포를 시도했다. | 기존 경로의 성공과 새 기본형의 미완료가 함께 있다. Preview·빌드·배포·실제 Agent 완료를 구분해야 하며 전원 동일 환경은 미확인이다. |
| 4일차 로그인과 DB | 로그인 화면을 추가하는 과정에서 빌드 실패를 관찰했고, Firebase 연결과 VS Code Agent 점검 방법을 다뤘다. | 강사 관찰로 앱 빌더 버튼의 Firebase 연결 성공을 기록했다. DB 종류·읽기/쓰기·전체 로그인 검증과 모든 학습자의 해결 여부는 별도 확인이 필요하다. |

팀은 성공 1건과 막힌 시도 1건 이상을 골라 “문제 → 가설 → 선택한 방법 → 실제 관찰 → 판단 → 다음 행동”으로 다시 설명한다. 성공 화면만 나열하지 말고, 그 선택이 기업 문제의 어느 부분을 해결했는지 연결한다.

## 3 막힌 과정에서 무엇을 배웠나

### 화면이 보이면 완성이라고 판단했던 지점

Hello World의 문구를 프롬프트로 수정했을 때 Preview에는 새 문구가 보였지만 기본 배포 버튼의 빌드가 실패했고 공개 화면에는 이전 문구가 남았다. “화면 생성”, “새 버전 배포”, “실제 업무 응답”의 완료 조건이 서로 다르다는 사례다. 팀은 자신이 성공이라고 적었던 항목의 근거를 다시 확인한다.

### 원인을 좁히기 전에 우회가 길어진 지점

서비스 개수 제한 가설을 확인한 뒤 배제했고, 감사 로그에서 서비스명 오류를 찾아 영문 이름으로 서비스 생성 단계를 통과했다. 이후 npm 설치 오류는 별도로 남았다. 최소 Hello World에서도 같은 설치 오류를 재현했으며, Node/npm과 설치 조건을 바꾼 별도 Cloud Shell 경로는 성공했다. 기본 버튼이 설정을 다시 생성하면서 오류가 반복된 기록도 있다. 따라서 별도 배포 성공을 기본 버튼 문제 해결로 바꿔 말할 수 없다. 당시 Google 이슈 등록은 조치 이력이며 현재 수정 여부를 뜻하지 않는다.

### 기능 추가와 검증 범위가 달라진 지점

로그인·DB·세션 같은 요구가 늘면 화면 변경뿐 아니라 의존성·서버·권한·저장 검증이 필요하다. 4일차에는 로그인 추가 후 빌드 실패와 Firebase 연결 성공을 각각 관찰했다. 로그인이나 Firebase 자체를 모든 실패의 원인으로 단정할 근거는 없다. 팀은 무엇을 바꿨고 어느 단계까지 확인했는지부터 정리한다.

### 다시 한다면 바꿀 진행 방식

다음은 회고를 통해 합의할 개선안이다. 모든 팀에 아래 문제가 실제로 발생했다고 전제하지 않는다.

| 점검할 진행 방식 | 다음에는 이렇게 바꾼다 |
| --- | --- |
| 같은 질문·자료·완료 조건을 정하기 전에 기능을 늘렸는가 | 대표 업무 질문과 원천 정답, 시작 버전을 먼저 합의한다. |
| 여러 조건을 바꾸고 무엇이 효과가 있었는지 놓쳤는가 | 한 번에 한 가지 가설을 시험하고 변경 전후를 남긴다. |
| 배포 실패를 오래 따라가며 업무 목표를 놓쳤는가 | 단계와 로그를 확보한 뒤 짧게 진단하고 분석·후속 과제로 전환한다. |
| 강사나 AI의 해결을 기다리며 판단을 맡겼는가 | 교육생이 가설·기대값·판정 이유를 먼저 쓰고 동료가 질문한다. |
| 자료 갱신과 운영 담당을 나중으로 미뤘는가 | 현업·데이터·IT 담당이 맡을 일을 로드맵에 함께 적는다. |

실패했다는 사실만으로 학습이 완성되지는 않는다. 무엇을 시도했고 어떤 증거로 다음 선택을 바꾸었는지 설명할 수 있어야 다음 실험에 도움이 된다.

## 5 컨설턴트의 진행 방법

### 도입에서 수업의 성격을 분명히 한다

“우리는 셀바스헬스케어의 제품 이력 확인 문제를 함께 풀어 왔습니다. 오늘은 각자가 어떤 시도를 했고, 무엇이 막혔으며, 어디까지 확인했는지 설명해 주세요. 제가 준비한 답을 듣기보다 서로의 근거를 검토하고 회사가 이어갈 다음 행동을 정하겠습니다. 막힌 부분에는 자료·환경·진행 방식에서 제가 보완할 일도 함께 적겠습니다.”

### 팀이 먼저 말하고 동료가 근거를 묻는다

처음 5분은 개인 기록, 다음에는 팀 공유를 한다. 컨설턴트가 먼저 원인을 말하지 않는다. “왜 이 방법을 골랐나요”, “그때 실제로 본 것은 무엇인가요”, “다른 원인이라면 어떤 결과가 나와야 하나요”, “업무 담당자가 안심하고 쓰려면 무엇을 더 확인해야 하나요”를 묻는다. 기록자가 관찰과 추정을 구분해 적고, 다른 팀이 빠진 근거를 확인한다.

실패 사례 50분은 개인 사례 선택 5분, 팀 내 설명 15분, 동료의 대안 질문 10분, 기존 근거 재확인 최대 10분, 다음 실험 정리 5분과 강사 안내 5분으로 운영한다. 사례가 여러 개면 두 개 이내로 좁힌다.

### 재실행은 판단을 위한 근거 확보에 쓴다

필요한 팀만 기존 대표 질문 1~2개나 저장된 로그를 확인한다. 실패 사례 시간 안에서 재실행은 최대 10분이다. 새 기능·새 환경 구축이나 반복 배포를 시작하지 않는다. 앱이 막히면 기존 응답·원천·비식별 로그로 분석한다. 직접 실행, 강사 시연, 저장된 결과 분석을 구분하고 실행하지 않은 검사는 미실행으로 남긴다. 빠른 팀은 다른 팀의 근거와 완료 조건을 검수한다.

### 개인의 학습과 시제품의 완성도를 나눠 본다

직접 실행하지 못한 교육생도 관찰·가설·검증 계획을 설명할 수 있다. 다만 분석 활동을 기능 실행 성공으로 바꾸어 적지 않는다. 각자 “내가 한 시도”, “판단을 바꾼 증거”, “다음에 혼자 할 수 있는 확인”을 한 가지씩 남긴다. 컨설턴트는 환경 준비·설명 부족·지원이 필요한 부분도 자신의 후속 과제로 받는다.

## 6 어디까지 왔는지 판정하기

팀은 항목별로 확인된 범위를 쓰고 근거가 없는 단계는 비워 둔다. 높은 단계로 자동 승격하지 않는다.

| 확인 범위 | 필요한 근거 |
| --- | --- |
| 시연 또는 저장 기록에서 확인 | 당시 앱·자료·화면·로그와 확인한 질문 |
| 본인이 직접 재현 | 본인 버전·자료·실행 시각·기대값·실제값 |
| 동료가 같은 조건으로 재현 | 동료의 독립 실행 결과와 달랐던 조건 |
| 제한된 현업 시험 준비 | 업무 담당자·승인된 자료·권한·오답 대응·중지와 지원 담당 |
| 운영 가능 여부 | 회사의 실제 데이터·권한·갱신·장애·비용·인수 기준에 따른 별도 검증 |

문제 정의, 원천 근거, 실패 원인 후보, 다음 검증이 서로 연결되는지 피드백한다. 이 수업의 기록은 공식 수료·합격 판정을 대신하지 않는다. 기존의 정상 10건 이상과 예외 시험 요구는 전체 인수 검증 과제로 유지한다. 오늘의 대표 사례 1~2건 확인으로 전체 검증 완료를 선언하지 않는다.

## 7 다음 실행을 회사의 과제로 바꾸기

팀마다 [후속 로드맵](../docs/day05-roadmap.md)을 읽고 세 가지 이내의 과제를 고른다. 각 과제에 책임자, 협업자, 필요한 지원, 확인 날짜, 완료 조건과 증거를 붙인다. 이름이 정해지지 않았으면 직무 역할과 담당자 확정 날짜를 적는다. 회사의 일정·자원 합의 전까지는 제안 일정으로 표시한다.

교육생은 현업 질문과 정답 검수, 실패 기록, 동료 재현, 첫 실행을 맡는다. 현업 책임자는 우선순위와 사용 범위를, 데이터 책임자는 필드 의미·자료 갱신과 기준 정답을, IT 담당은 접근·배포·권한과 운영 지원을 맡는다. 컨설턴트는 질문을 검증 가능한 과제로 바꾸고 다음 점검에서 근거와 판단을 함께 검토한다. 도구 사용의 숙련도 외에도 이 역할 수행을 위한 시간과 회사 지원이 필요하다.

팀 발표는 문제와 선택 이유 1분, 시도와 실패 근거 1분, 현재 한계와 다음 행동 1분으로 한다. 동료는 “어떤 증거가 더 필요하나”를 한 가지 묻는다. 전체 발표는 시간 안에 가능한 2~3팀을 선정하고 모든 팀의 기록은 서로 교차 검수한다. 모든 교육생은 개인 실행 약속을 남긴다.

## 8 준비와 종료 확인

강사는 기존 원천, 성공·실패 응답, 배포 단계별 비식별 로그와 [PBL 회고 활동지](../worksheets/day05-pbl-retrospective.md)를 준비한다. 사전에 팀별 앱 접근 가능 여부와 자료 버전을 확인한다. 원천 정답은 [4일차 기록지](../worksheets/day04-baseline-and-questions.md)를 재사용하되 ERP 20행·SW 10행 묶음과 Day 1 CSV를 섞지 않는다.

종료 시 팀별 문제 한 문장, 시도·의사결정 기록, 현재 수준표, 우선 과제 3개 이내의 로드맵과 개인별 첫 행동이 있어야 한다. 미확인·미실행도 남긴다. 제출 위치와 다음 점검 날짜는 수업에서 합의한다. 공개 저장소에는 교육용 가상 사례와 양식만 올리고 실제 업무 자료와 작성된 개인 기록은 승인된 내부 위치에 둔다.
