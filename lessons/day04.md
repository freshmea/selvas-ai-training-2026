# 4일차 · Google Cloud Agent로 교육 전환과 공통 베이스라인

진행 기록일: **2026-10-21**. 다음 교육일: **2026-10-22**.

[Notion 4일차 자료](https://app.notion.com/p/400123060ee781aa855fc0d1ee62e06e) · [검증 기록지](../worksheets/day04-baseline-and-questions.md)

이 자료는 강사가 전달한 오전 안내와 이후 앱 배포·검증 작업 및 대화를 정리한 기록이다. 아래 작업 내역이 교육생 전원의 개별 수행이나 동일 환경 구축 완료를 뜻하지는 않는다. 기존 4일차의 미해결 문의·직원 이용 경로 운영안은 [커리큘럼](../docs/curriculum.md)에 유지한다.

## 1. 오전에 안내한 교육 방향

강사는 오전에 교육생이 만든 **Google Chat + Google Apps Script + Gemini API** 방식과 **Google Cloud Agent** 방식의 기능·구조 차이를 설명했다. 이후 남은 교육은 Google Cloud Agent를 중심으로 진행하고, 모두 같은 베이스라인에서 다음 날부터 기능을 추가하며 질문을 검증하겠다고 안내했다.

오늘의 목적은 각자 다른 구현을 계속 확장하는 데서 공통의 출발점을 맞추는 것으로 옮겨갔다. 공통 베이스라인은 같은 화면만을 의미하지 않는다. 기능 요구, 더미 데이터 규칙, 실제 Agent 연결 방식, 정답표와 시험 절차를 공유하되 **각자의 프로젝트와 Agent 실행 ID는 구분**해야 한다.

**안내한 방향은 확정되었지만 전원 동일 베이스라인 검증 완료는 아직 확인되지 않았다.** 내일 시작할 때 계정별 상태를 먼저 점검한다. 새로운 앱의 생성 재시도는 시간이 지난 뒤 진행하기로 했으며, 이 기록 작성 과정에서는 재시도하지 않았다.

## 2. 두 방식의 기술적 차이와 선택 이유

| 항목 | Google Chat + Apps Script + Gemini API | Google Cloud Agent + 앱 빌더 |
| --- | --- | --- |
| 사용자 진입점 | Google Chat의 메시지를 Apps Script가 받음 | 앱 빌더가 만든 웹 UI 등에서 Agent를 호출 |
| 처리 흐름 | 스크립트가 자료 조회·프롬프트 구성·Gemini 호출·응답을 명시적으로 구현 | Agent가 지침·도구·구성된 하위 Agent로 판단하고, 앱은 입력·근거 선별·표시를 담당 |
| 대화 이어가기 | `generateContent`에 이전 대화를 전달하거나 별도 저장하는 처리가 필요 | A2A `contextId`와 앱의 선택 장비 상태를 이어가는 처리가 필요 |
| 문맥의 한계 | 단발 호출만 구현하면 앞선 장비나 질문을 기억하지 못함 | `contextId`만 있다고 사용자 구분·영구 이력·접근 통제가 완성되지는 않음 |
| 계정·설정 | 이번 실습에서 Apps Script 기반 Chat 앱 등록의 Workspace 계정·조직 설정 제약을 만남 | Cloud 프로젝트·API·실행 주체 권한·Agent 리전·실행 ID·웹 배포 설정을 확인 |
| 비용 확인 | Gemini API의 적용 등급·한도·사용량과 기존 서비스 조건을 확인 | 모델/Agent 호출과 Cloud Run·빌드 등 사용 서비스별 비용·한도를 확인 |
| 검증할 대상 | 스크립트의 조회 규칙, 모델에 전달한 근거, Chat 응답 | 앱의 정확 조회, 실제 Agent 호출, 완료 응답, 배포 버전과 직원 이용 경로 |

Chat은 대화 채널이며 Gemini API는 모델 호출 수단이다. Cloud Agent를 선택했다고 Chat이 필수로 연결되거나 기존 스크립트의 모든 기능이 자동 이관되는 것은 아니다. 이번 교육에서는 **Agent의 역할·근거·예외·후속 질문을 공통으로 검증하기 위해 Cloud Agent 경로를 중심으로 통일**한다.

여기서 앱 빌더는 **Google Cloud의 Agent Studio 안에 있는 앱 빌더**다. 별도 서비스인 Google AI Studio와 혼동하지 않는다. Agent Designer의 지침, Runtime의 실행 버전, 앱 빌더의 편집본, Cloud Run의 배포본은 각각 확인한다. 구체적인 비교와 이전 실측은 [Notion 3일차 자료](https://app.notion.com/p/3ff123060ee781c28259cc1aa9cd63cc)를 함께 읽는다.

## 3. 오늘 작업의 흐름

1. 교육생이 공유한 앱과 배포 로그를 확인했다. 미리보기는 나오지만 배포 시 의존성 설치에서 실패하는 상황을 분리했다.
2. 검증된 배포 파일을 이용한 `gcloud` 경로에서 계정별 프로젝트·Agent 연결·필요 API·공개 접속·실제 응답을 확인했다. 확인된 계정의 결과만 성공으로 기록했다.
3. 이후 수정 요청을 앱 빌더 프롬프트로 반영하고 배포 버튼으로 게시할 수 있도록 제작 이력을 유지하는 방향을 시도했다.
4. 앱 빌더가 내보내는 빌드 구조와 기존 검증 ZIP의 구조가 달라, 기존 ZIP의 성공을 앱 빌더 버튼 배포의 성공으로 옮길 수 없음을 확인했다.
5. 버전 고정·의존성 보완 등 여러 시도를 했지만 실제 Cloud Build 실패가 남았다. 사용자는 우회가 길어지는 점을 지적하고, 앱 빌더에서 처음부터 기능 요구 프롬프트로 생성하도록 방향을 정했다.
6. 프롬프트만으로 기본 UI와 ERP 20행·SW 10행의 더미 자료를 생성·저장했다. 이후 확장 생성은 `Resource has been exhausted`로 실패했다. 사용자는 시간이 지난 뒤 재시도하고 오늘 작업을 교육 기록으로 남기기로 했다.

## 4. 문제·증거·대응·남은 상태

| 문제 | 확인한 현상·증거 | 대응과 배운 점 | 현재 판정 |
| --- | --- | --- | --- |
| 미리보기는 정상인데 배포 실패 | Cloud Build의 Step 6 `RUN npm install`에서 `Cannot read properties of null (reading 'edgesOut')` | 미리보기 환경과 새 Linux 컨테이너의 설치·빌드를 분리. 실제 배포 로그로 판단 | 앱 빌더 버튼 배포 문제 미해결 |
| npm 업그레이드 오류라는 오해 | 오류 아래에 npm 10.8.2 → 12.2.0 업데이트 안내가 함께 출력됨 | 업데이트 안내는 실패 원인 자체가 아님. 핵심은 설치 중 의존성 처리 오류 | 오류 해석 정리 완료 |
| 텍스트·ZIP 전달 후 재현성 부족 | 원본 ZIP에도 가변 버전이 있었으며, 내보내기 시 루트·backend·Dockerfile 구성이 재생성됨 | 텍스트 공유만 원인으로 단정하지 않음. package.json·lockfile·빌드 입력·Node/npm 환경을 함께 봄 | 진단 자료 작성, 원인 전부 확정 아님 |
| 검증 ZIP과 앱 빌더 기본 구조 차이 | 별도 검증 파일은 고정 버전·`npm ci`·서버 인증 연결을 사용. 앱 빌더 기본 배포 구조와 다름 | 별도 `gcloud` 성공과 앱 빌더 버튼 배포를 구분. 로컬 설치 성공으로 Linux 배포 성공을 선언하지 않음 | 기존 경로 성공 / 기본 경로 미해결 |
| 의존성 우회가 길어짐 | 버전 고정과 추가 의존성 반영 후에도 실제 Linux 빌드 실패가 남음 | 추가 우회를 멈추고 기본 환경에서 기능 요구로 새로 생성하는 방식 채택 | 제작 방향 변경 완료 |
| 계정·Agent 연결 혼선 | 브라우저 프로필과 로그인 계정 불일치, 교육생마다 다른 프로젝트·Agent 실행 ID | 연결된 계정을 확인하고 본인 프로젝트·리전·Agent ID로 검증. API·권한도 개별 확인 | 검증한 계정에 한해 확인, 전원 완료 미확인 |
| 인증 화면·브라우저 연결 문제 | 비공개 서비스는 인증 필요. 연결 서버는 실제 미리보기 출처와 CORS 설정이 맞아야 함 | 승인된 더미 앱은 공개 접속으로 검증. 기존 미리보기의 실제 출처를 맞춰 Agent 연결 확인 | 기존 검증 앱에서 해결, 새 앱 검증 별도 |
| 생성 모델 한도 초과 | 서로 다른 생성 모델에서도 `Resource has been exhausted`, 후속 생성이 롤백됨 | 무조건 코드 오류로 분류하지 않음. 생성 한도 문제와 실행 Agent의 429를 구분 | 재시도 보류, 해결 확인 안 됨 |

`package-lock.json`과 `npm ci`는 설치 재현성을 높이는 수단이다. lockfile 하나를 추가하면 모든 `edgesOut` 오류가 사라진다는 보장은 없다. 이번 앱 빌더 기본 배포 실패의 근본 원인은 확정하지 못했으며, [배포 오류 진단 교안](../docs/deployment/text-sharing-build-failures.md)에 로그 해석과 재현 조건을 남겼다.

## 5. 주요 대화와 의사결정

아래는 실제 요청과 대응의 **요약이며 축어록이 아니다**. 교육생이 직접 하지 않은 발언이나 확인하지 않은 동의를 덧붙이지 않았다.

| 대화의 쟁점 | 요청·질문의 요지 | 대응·결정 |
| --- | --- | --- |
| 교육 방향 | 오전에 Chat·Gemini API와 Cloud Agent의 차이를 설명하고 남은 교육 경로 안내 | Cloud Agent를 중심으로 통일하고 다음 날부터 공통 기준에서 기능·질문 검증 |
| 미리보기와 배포 | 화면이 나오면 빌드도 정상인 것 아닌가? | 미리보기 실행과 배포 컨테이너의 새 의존성 설치가 별도임을 설명하고 실제 로그 확인 |
| 프롬프트로 수정 | 시스템을 직접 바꾸기 어려우니 AI에 요청할 수정 프롬프트도 필요 | 재현 가능한 요청문을 Markdown으로 저장. 파일 하나만으로 해결되었다고 기록하지 않음 |
| 교육생별 배포 | 검증된 파일을 쓰고 코드 재생성 없이 배포·속도·Agent만 검증 | 기존 검증 파일의 `gcloud` 배포와 실제 호출을 계정별로 확인 |
| 연결 대상 | Agent 주소는 교육생마다 생기는 ID로 확인해야 함 | 공통 코드를 쓰더라도 프로젝트·리전·Runtime ID는 계정별로 확인 |
| 수정·게시 경로 | 이후에는 빌더 기능을 적극 사용하고 버튼으로 배포하고 싶음 | Google AI Studio가 아니라 Google Cloud 앱 빌더임을 바로잡고 제작 이력과 배포를 구분 |
| 과도한 우회 | 기존 기능과 앱 빌더 기본 버전을 유지할 수 없는가? | 기존 정상 앱을 유지하면서 새 기본형을 프롬프트로 만드는 방향 채택 |
| 최소 참조 코드 | 처음부터 프롬프트만으로 기능을 완성하고 코드는 필수 부분만 참조 | 전체 소스·ZIP 대신 기능 요구문과 최소 A2A 요청 JSON을 제공 |
| 종료와 다음 행동 | 시간이 지난 후 시도하고 지금까지를 4일차 자료로 남기자 | 생성 재시도를 보류하고 문제·대응·대화·미완료·다음 날 계획을 문서화 |

## 6. 실제 속도 측정: 기존 배포 앱의 결과

아래 수치는 **기존 검증 파일을 `gcloud`로 배포한 교육생 앱**의 기록이다. 새 프롬프트 기본형의 측정값이 아니다. 외부 HTTP 요청에는 IAM 토큰을 넣지 않고 공개 Cloud Run에 접속했으며, 서버가 인증하여 실제 Agent를 호출했다.

통합 5회는 새 문맥으로 실행했으며 일부 구간에는 브라우저 요청이 한 건 겹쳤다. 완전히 격리된 단일 요청 성능 시험으로 해석하지 않는다.

| 시험 | 측정값 | 관찰과 해석 |
| --- | --- | --- |
| 제품이력 통합 질문, 외부 HTTP 5회 | 18.911 / 17.085 / 25.259 / 25.007 / 16.778초 | 평균 **20.608초**, 중앙값 **18.911초**. 완료 응답 확인 |
| ERP 출고일 단독, 외부 HTTP 1회 | **5.126초** | 통합 질문과 처리 범위가 달라 직접 성능 우열로 일반화하지 않음 |
| 통합 질문, 브라우저 1회 | **20.447초** | 브라우저에서 본 완료 시간으로 외부 HTTP와 측정 경계 구분 |
| 후속 제조일 질문 | 첫 시도 429 관련 오류, 재시도 **5.820초** | 재시도에서 ERP #1 제조일 2026-01-20 확인. 실패를 성공 통계에서 숨기지 않음 |

정상 HTTP 6건(통합 5건 + 단독 1건)은 Task 완료와 폴링 0회를 확인했다. 다른 시도의 HTTP 200에 포함된 `WORKING`·`ResourceExhausted`는 정상 완료로 판정하지 않았다. HTTP 상태, Task 상태, 실제 답을 함께 봐야 한다.

기존 Agent가 앱에서 전달하지 않은 스냅샷 날짜나 샘플 열 설명을 덧붙인 사례도 있었다. 이를 검증된 메타데이터로 취급하지 않으며, 호출 완료와 답변 전체의 정확성 판정을 구분한다.

이 결과는 소수 질문의 응답 시험이다. 10만~100만 행의 조회 성능이나 동시 사용자 부하를 입증하지 않는다. 하위 Agent 두 개가 있다는 사실만으로 지연의 원인을 확정할 수도 없다. 질문 범위, 자료 선별, 모델 호출, 도구·하위 Agent 실행, 재시도 시간을 나눠 기록해야 한다.

## 13. 서비스 개수 제한 확인과 배포 실패 원인 발견

사용자는 기존 서비스는 배포됐는데 새 앱이 안 되는 이유가 개수 제한인지 질문하고, 제한이 원인이면 기존 것을 해제하고 새 앱을 배포해 달라고 요청했다. 프로젝트의 실제 할당량을 확인했다.

| 이름 수정 전 검사 항목 | 실제 사용 / 한도 | 판정 |
| --- | --- | --- |
| Cloud Run 서비스 수, us-west1 | 2 / 1,000 (0.2%) | 여유 |
| Cloud Run 서비스 수, us-central1 | 1 / 1,000 (0.1%) | 여유 |
| Cloud Build CPU, cloud-run용 us-west1·us-central1 | 각 2 / 40 (5%) | 여유 |
| Cloud Run CPU, us-west1 | 1,000 / 200,000 milli-vCPU (0.5%) | 여유 |

서비스 수의 [공식 기본 한도](https://docs.cloud.google.com/run/quotas)는 프로젝트·리전별 1,000개이며, 이번에는 실제 적용 값도 확인했다. 개수 부족이 아니므로 기존 서비스를 삭제하지 않았다.

Cloud Logging에서 배포 시각의 `CreateService` 감사 로그를 조회하자 화면의 일반적인 서버 무응답 안내와 다른 구체적 오류가 있었다.

```text
service.metadata.name: must not contain tag delimiter '---'.
```

실패한 이름은 `genai-app---1-…` 형태였다. 한글 위주 앱 이름을 서비스명으로 변환할 때 영문 부분이 비어 생긴 것으로 보인다. **서비스명이 금지된 세 하이픈을 포함했다는 점은 로그로 확인했으며, 이름 변환의 내부 구현은 추정이다.**

앱 제목을 클릭해 저장되는 이름을 `product-history-prompt`로 바꿨다. 기능 코드나 더미 자료를 직접 수정하지 않고 같은 앱의 배포 버튼을 다시 눌렀다. 이후 `genai-app-product-history-prompt-1-…` 서비스가 생성되고 실제 Cloud Build가 시작돼, 서비스명 문제를 통과한 것을 확인했다.

그러나 새 빌드는 38초 후 **Node 20 기본 템플릿의 Step 6 `RUN npm install`에서 `Cannot read properties of null (reading 'edgesOut')`로 실패**했다. 앞서 성공한 별도 gcloud 검증본의 Node 22·고정 의존성·`npm ci` 경로와 앱 빌더의 자동 생성 템플릿은 다르다. 기존 성공이 새 기본 템플릿의 설치 성공을 보증하지 않는다.

**이번에 해결:** 개수 제한 가설 배제, 감사 로그로 서비스명 검증 오류 특정, 영문 이름으로 서비스 생성·빌드 시작 성공.

**남은 문제:** 앱 빌더 자동 템플릿의 npm 설치 실패. 최종 실행 가능한 새 공개 URL과 배포본 속도 검증은 여전히 미완료다. 기존 서비스와 실제 Agent 연결 서버는 유지했다. 이름 문제를 npm 문제의 해결책으로 제시하지 않는다.

## 14. Hello World로 분리한 npm 오류와 수정 실험

사용자는 복잡한 기능을 제거하고 Hello World만 표시하는 앱도 배포되는지 확인해 달라고 요청했다. 최소 HTML 형식을 엄밀히 따지기보다 배포 오류 여부를 우선 확인하라는 후속 지시에 따라, 생성된 기본형으로 배포했다. 미리보기·업로드·Docker 준비와 파일 복사는 통과했지만 **총 37초 후 Step 6 `RUN npm install`에서 동일한 `edgesOut` 오류**가 발생했다. 따라서 제품이력 업무 코드와 Agent/subagent 실행이 이 실패의 재현에 필요하지 않음을 확인했다.

기존 성공 앱과 신규 실패 앱은 같은 빌드 조건이 아니었다. 강사 계정의 기존 고정응답·제품이력 직접 배포본은 Node 22에서 frontend/backend를 각각 설치했다. 이후 교육생용 검증 ZIP은 Node 22.22.0·lockfile·`npm ci`를 사용했다. 앱 빌더 기본 템플릿은 Node 20/npm 10.8.2에서 루트 workspace 의존성을 새로 계산했다.

npm 공식 [수정 PR #8448](https://github.com/npm/cli/pull/8448)은 `loadPeerSet`의 부모 없는 노드 참조 결함을 다루며 2025-08-28 병합됐다. [후속 이슈 #9787](https://github.com/npm/cli/issues/9787)에는 패키지 조합별 추가 재현·우회 사례가 있다. 이번 현상은 알려진 결함과 부합하지만 Google의 템플릿 내부 원인을 모두 확인한 것은 아니다.

실패한 실제 ZIP을 Cloud Shell에서 받아 **업무 소스와 세 package.json을 유지한 채 Docker의 Node를 22.22.0, npm을 11.12.1로 고정**한 대조 빌드는 패키지 설치·Vite 빌드·최종 이미지 생성까지 성공했다. 이후 루트 lockfile과 `npm ci`를 사용하는 재현 가능한 최종 빌드를 추가 검증했다. [수정 내역·공식 근거·재현 프롬프트](../prompts/hello-world-build-repair.md)에 실행 절차를 정리했다.

이 수정은 Cloud Shell에서 관리하는 배포 소스에 적용한 것이다. 앱 빌더 기본 배포 버튼의 자동 생성 템플릿이 영구 수정됐다는 뜻은 아니다. 기존 제품이력 앱·Agent의 배포와 속도 결과도 이번 Hello World의 성공으로 대체하지 않는다.

**최종 검증:** lockfile과 `npm ci`를 사용한 실제 Linux Cloud Build도 SUCCESS. 성공 이미지 digest를 기존 Hello World 서비스에 적용해 Ready=True와 최신 리비전 트래픽 100%를 확인했다. 공개 브라우저에서 Hello, world가 표시됐고, 별도 인증 헤더 없는 외부 HTTP 요청도 200으로 본문을 확인했다. 해결된 범위는 이 Hello World 배포본이며, 제품이력 앱의 기본 버튼 배포는 별도 후속 작업이다.

## 15. 프롬프트 수정 후 기본 배포 버튼의 인수 시험

사용자는 완료 조건을 **프롬프트로 Hello, world를 Edited world로 변경 → 기존 Cloud Run 앱 업데이트 버튼 → 빌드 성공 → 배포 화면의 변경 확인**으로 정했다. gcloud로 수정한 이미지가 실행된다는 사실만으로 이 조건을 충족하지 않는다.

실제 프롬프트 수정·저장과 미리보기의 Edited world 표시는 성공했다. 그러나 기본 버튼이 시작한 새 Cloud Build는 **36초 후 같은 `edgesOut` 오류로 실패**했다. 실제 새 배포 ZIP에는 변경 문구가 들어갔지만 Node 20 기반 루트 `npm install` 구조가 다시 생성됐고 lockfile은 없었다. 기존 공개 서비스는 HTTP 200으로 Hello, world를 계속 표시했다. 따라서 HTTP 200은 새 수정본의 게시 성공 증거가 아니었다.

공개 콘솔 코드를 추적하니 기본 버튼이 Dockerfile과 workspace manifest를 매번 생성하고, importmap의 패키지 버전을 제거해 `latest`로 지정하는 구조를 확인했다. 승인 목록 밖의 패키지를 추가하는 별도 대조 빌드는 성공했지만 모델의 정상 편집 과정에서 해당 항목이 제거되어 기본 버튼 해결책으로 유지되지 않았다. 승인 필터를 우회하거나 콘솔 코드를 변조하지 않았다.

이후 확인한 범위는 다음과 같다.

| 후속 확인 | 결과 |
| --- | --- |
| 영어 콘솔로 바꾸면 해결되는가 | 현재 영어 페이지의 공개 번들도 같은 Node 20·루트 npm 설치·템플릿 리비전 2026-09-02를 사용했다. 언어 변경으로 해결된 근거 없음 |
| 서비스의 빌드 설정으로 Node/npm을 고정할 수 있는가 | 공식 DockerBuild API에는 옵션 필드가 없고, 현재 기본 버튼 요청에서 기존 사용자 빌드 설정을 합치는 분기를 찾지 못함 |
| 빌드 환경변수로 npm 옵션을 바꿀 수 있는가 | 공식 문서는 buildpacks에 전달하는 설정으로 설명. 현재 명시적인 Docker 빌드의 영구 수정 수단으로 확인되지 않음 |
| 앱에 `.npmrc`를 넣으면 되는가 | 앱 파일은 frontend 아래로 수집되고 최초 설치 뒤 복사됨. 실패하는 설치 전에 `.npmrc`가 들어가는 구조가 아님 |
| 별도 GitHub/CI 자동 배포로 전환할 것인가 | 대안으로 제안했으나 사용자가 기존 Cloud Run 버튼만 사용하도록 명확히 함. 새 저장소·트리거·IAM 역할을 생성하지 않음 |

근거: [Google Docker 빌드 proto](https://github.com/googleapis/googleapis/blob/master/google/cloud/run/v2/build.proto), [빌드 환경변수 안내](https://docs.cloud.google.com/run/docs/configuring/services/build-environment-variables), [상세 조사·재현 요청문](../prompts/hello-world-build-repair.md).

**현재 판정: 바이브 코딩 공통 베이스라인은 미완성이다.** 확인한 공식 설정과 기본 버튼 구조에서는 빌드 설정을 영구 고정하는 경로를 확보하지 못했다. Google이 생성하는 배포 템플릿의 수정이 필요한 차단점으로 판단하며, 기본 버튼 인수 시험이 통과하기 전에는 해결 완료라고 교육하지 않는다. 기존 gcloud 배포본의 성공과 실제 Agent 응답 기록은 그 확인 범위 안에서 유지한다.

## 16. Google 오류 신고와 남은 확인

사용자 요청에 따라 Cloud 콘솔에서 의견 보내기와 재시도를 실행했지만 모두 **“의견을 보낼 수 없습니다”**로 실패했다. 이 경로의 접수 완료는 확인되지 않았다.

등록 전 공식 Vertex AI Studio Issue Tracker에서 `componentid:1849271 edgesOut` 조건으로 검색했을 때 일치 항목은 없었다. 이후 사용자가 약관·공개 신고에 동의하고 CAPTCHA를 직접 완료해 **공식 Bug [#576177987](https://issuetracker.google.com/issues/576177987)을 등록했다.** 실제 생성 페이지에서 첫 댓글 시각 **2026-10-21 23:57 KST**와 등록 당시 상태 **New**를 확인했다. 콘솔 피드백 두 차례는 실패했지만 공식 이슈 등록은 완료됐다. Google의 원인 인정·답변·수정 일정은 아직 없고 기본 버튼 문제도 미해결이다.

신고 내용에는 단순 Hello World에서도 실패한다는 점, 기본 생성 환경과 npm 오류, Node/npm만 함께 바꾼 Linux 대조 성공, 다음 버튼 요청의 설정 재생성, 프롬프트 수정본의 게시 실패를 포함한다. 공개 교육 자료에는 프로젝트·Agent 식별자, 계정 이메일, 실제 배포 주소, 토큰이나 비밀값을 싣지 않는다. [공개용 신고 요약과 접수 상태](../prompts/hello-world-build-repair.md#google-오류-신고-상태)에 재현 절차를 남겼다.

후속 검증은 Google의 안내 또는 수정된 기본 템플릿이 제공된 뒤 동일한 인수 시험을 다시 실행하는 것이다. 확인할 것은 프롬프트 저장, 실제 새 빌드의 성공, 새 리비전의 준비 상태, 배포 화면의 Edited world 반영이다. 임의의 수동 배포로 이 시험을 대체하지 않는다.

## 17. 수업 진행용 대체 실습: 미리보기·ZIP·gcloud 배포

2026-10-22 사용자 요청으로 [교육생용 순서별 실습 안내](../docs/deployment/app-builder-zip-gcloud.md)를 추가했다. 앱 제작과 수정은 앱 빌더 프롬프트로 진행하고, 최신 소스 ZIP을 Cloud Shell로 옮겨 검증된 배포 원본에 반영한 뒤 gcloud로 빌드·배포한다. 기본 버튼 오류의 해결 완료와 구분하는 수업 진행 경로다.

안내에는 계정·프로젝트·본인 Agent ID 확인, ZIP 업로드, API·결제·세 주체의 권한, Artifact Registry, 배포 원본 백업, Node/npm·lockfile, 실제 빌드·배포 명령, 실행 URL·리비전·Agent·대화·지연 검증, 두 번째 프롬프트 수정 후 같은 서비스 재배포를 포함했다.

**핵심 준비물:** 앱 빌더 다운로드 ZIP은 확인한 구조상 로컬 실행용이다. 최신 화면 소스만 가져오고, 본인용으로 검증된 backend·Dockerfile·manifest·lockfile과 Agent 인증 연결은 유지한다. 이 기준 원본이 없는 교육생의 첫 배포 준비와 기존 앱의 반복 업데이트를 구분한다. 단순 다운로드 ZIP 전체를 운영 원본 위에 덮어쓰는 절차로 안내하지 않는다.
